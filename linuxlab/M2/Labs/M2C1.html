Laboratorio M2C1 - Usuarios y grupos POSIX

Investigación experimental de la identidad de las cuentas Linux y de las credenciales de grupo asociadas a los procesos.

user-management uid-gid supplementary-groups process-credentials access-troubleshooting

>_ Relevancia Operativa

Este laboratorio demuestra la capacidad práctica para consultar e interpretar la identidad de usuarios y grupos en Linux mediante herramientas como id y getent, e inspeccionar las credenciales asociadas a procesos en ejecución mediante /proc/<PID>/status.

También demuestra la capacidad de investigar incidencias de acceso relacionadas con cambios en la pertenencia a grupos, distinguiendo entre la información actual de una cuenta y las credenciales que conserva un proceso en ejecución.

Objetivos

  • Analizar cómo representa Linux la identidad de usuarios y grupos, relacionando los nombres de las cuentas con sus UID y GID, y localizando la información correspondiente mediante archivos como /etc/passwd y /etc/group y herramientas como id y getent.
  • Diferenciar la identidad de una cuenta de las credenciales de un proceso en ejecución, identificando los UID y GID reales y efectivos, así como los grupos suplementarios, mediante la inspección de /proc/<PID>/status.
  • Investigar el efecto de los cambios en la pertenencia a grupos sobre los procesos existentes, contrastando la información de la cuenta antes y después del cambio con las credenciales de procesos ya iniciados y de nuevas sesiones.

Proceso utilizado

Proceso de control identity.py

#!/usr/bin/env python3
import os
import pwd
import grp
import time

def get_group_names(gids):
    """Traduce una lista de GIDs a sus nombres correspondientes."""
    names = []
    for g in gids:
        try:
            names.append(f"{g} ({grp.getgrgid(g).gr_name})")
        except KeyError:
            names.append(str(g))
    return names

def main():
    # Obtención de credenciales a nivel de proceso
    pid = os.getpid()
    uid = os.getuid()
    gid = os.getgid()
    euid = os.geteuid()
    egid = os.getegid()
    supplementary_gids = os.getgroups()

    # Traducción de UID y GID primario a nombres
    try:
        user_name = pwd.getpwuid(uid).pw_name
    except KeyError:
        user_name = "Desconocido"

    try:
        group_name = grp.getgrgid(gid).gr_name
    except KeyError:
        group_name = "Desconocido"

    print(f"=== INFORMACIÓN DE CREDENCIALES DEL PROCESO ===")
    print(f" PID (Process ID)       : {pid}")
    print(f" UID (Real / Efectivo)  : {uid} ({user_name}) / [Efectivo: {euid}]")
    print(f" GID (Primario / Efect.) : {gid} ({group_name}) / [Efectivo: {egid}]")
    print(f" Grupos Suplementarios  : {', '.join(get_group_names(supplementary_gids))}")
    print("=" * 48)
    print("El proceso se mantendrá en ejecución para inspección...")
    print("Pulsa Ctrl+C para finalizar.")

    # Bucle infinito controlado para mantener el proceso vivo
    try:
        while True:
            time.sleep(10)
    except KeyboardInterrupt:
        print("\n[!] Proceso finalizado por el usuario.")

if __name__ == "__main__":
    main()

El script consulta las credenciales de identidad del proceso en ejecución, muestra los UID y GID reales y efectivos, traduce los identificadores a nombres de usuario y grupo cuando es posible, y permanece activo para permitir su inspección desde otra terminal.

1. Importación de módulos

El script utiliza módulos de Python para consultar las credenciales del proceso, traducir identificadores numéricos a nombres y mantener el proceso activo durante la inspección.

  • os: proporciona funciones para consultar el PID y las credenciales del proceso.
  • pwd: permite consultar la base de cuentas de usuario.
  • grp: permite consultar la base de grupos.
  • time: proporciona la función sleep() para mantener el proceso activo sin consumir CPU innecesariamente.

2. Traducción de GID a nombres de grupo

La función get_group_names(gids) recibe una lista de identificadores de grupo (GID) e intenta obtener el nombre asociado a cada uno. Si no encuentra una correspondencia, captura la excepción KeyError y conserva el identificador numérico.

  • grp.getgrgid(g).gr_name: obtiene el nombre asociado al GID.
  • names.append(f"{g} ({grp.getgrgid(g).gr_name})"): almacena el identificador junto con el nombre del grupo.
  • names.append(str(g)): conserva el GID como texto cuando no se encuentra el grupo.

3. Obtención de las credenciales del proceso

Dentro de main(), el script consulta los identificadores del proceso actual. Estos valores permiten distinguir entre las credenciales reales y efectivas, así como conocer los grupos suplementarios asociados al proceso.

  • os.getpid(): obtiene el identificador del proceso (PID).
  • os.getuid() y os.getgid(): obtienen el UID y el GID reales.
  • os.geteuid() y os.getegid(): obtienen el UID y el GID efectivos.
  • os.getgroups(): obtiene la lista de grupos suplementarios del proceso.

4. Traducción de UID y GID a nombres

El script consulta las bases de usuarios y grupos para obtener los nombres asociados a los identificadores numéricos. Si no encuentra una correspondencia, captura la excepción KeyError y utiliza el texto Desconocido.

  • pwd.getpwuid(uid).pw_name: obtiene el nombre de usuario asociado al UID real.
  • grp.getgrgid(gid).gr_name: obtiene el nombre del grupo asociado al GID real.

5. Presentación de resultados

Las instrucciones print() muestran los datos recopilados, facilitando la interpretación de las credenciales y su posterior comparación con la información disponible en /proc/<PID>/status.

  • PID: identifica el proceso en ejecución.
  • UID (Real / Efectivo): muestra el UID real y el efectivo.
  • GID (Primario / Efect.): muestra el GID real y el efectivo.
  • Grupos Suplementarios: muestra los GID suplementarios junto con sus nombres cuando están disponibles.

6. Bucle de ejecución continua

El bucle infinito mantiene el proceso activo mediante llamadas a time.sleep(10). Esto permite inspeccionarlo desde otra terminal mientras permanece en ejecución, sin generar mensajes periódicos ni escribir en un archivo de registro.

  • while True: repite la ejecución indefinidamente.
  • time.sleep(10): suspende la ejecución durante diez segundos en cada iteración.

7. Finalización mediante Ctrl+C

El bloque except KeyboardInterrupt captura la excepción generada normalmente cuando Python recibe SIGINT al pulsar Ctrl+C desde la terminal interactiva. El script muestra un mensaje de finalización y termina al salir de la función main().

  • except KeyboardInterrupt: captura la interrupción.
  • print("\n[!] Proceso finalizado por el usuario."): muestra el mensaje de finalización.
  • Al finalizar normalmente la función main(), el proceso termina con código de salida 0.
Observación. os.getgroups() devuelve los grupos suplementarios del proceso; según el sistema y la configuración, la lista puede incluir también el GID primario. Conviene interpretar su salida junto con los campos Gid y Groups de /proc/<PID>/status, sin asumir que ambas listas representan categorías completamente independientes.

Experimento 1 - Identidad de cuenta y almacenamiento de la información

Hipótesis

  • Si se consulta una cuenta de usuario, se puede relacionar su nombre con un UID único.
  • Si se consulta la identidad de un usuario, se puede identificar un grupo primario asociado a su cuenta.

Observación

1. Comando id

M2user1@ubuntu-lab:~$ id
uid=1001(M2user1) gid=1003(M2user1) groups=1003(M2user1),1001(M2shared),1002(M2extra)
  • uid=1001(M2user1) La identificación numérica de usuario en el núcleo del sistema es 1001 y el nombre de la cuenta es M2user1.
  • gid=1003(M2user1) El grupo principal es el 1003 y su nombre es M2user1. Este es el grupo que se le asignará por defecto a cualquier archivo que se cree.
  • groups=1003(M2user1),1001(M2shared),1002(M2extra) Lista de todos los grupos a los que pertenece.

2. Consulta de la base de datos mediante getent passwd 

M2user1@ubuntu-lab:~$ getent passwd M2user1
M2user1:x:1001:1003::/home/M2user1:/bin/bash

Información de la cuenta obtenida de la base de datos de usuarios /etc/passwd.

  • M2user1 Nombre de usuario.
  • x Indicador de que la contraseña cifrada (hash) se almacena normalmente en /etc/shadow.
  • 1001 UID del usuario.
  • 1003 GID del grupo principal del usuario.
  • /home/M2user1 Ruta absoluta del directorio personal home.
  • /bin/bash Intérprete de comandos predeterminado que se le asigna al iniciar sesión.

3. Consulta de la base de datos mediante getent group 

M2user1@ubuntu-lab:~$ getent group | grep M2
M2shared:x:1001:M2user1,M2user2
M2extra:x:1002:M2user1
M2user1:x:1003:
M2user2:x:1004:

Filtro de los grupos del sistema que contienen M2, mostrando el mapa de membresías.

  • M2shared Grupo con GID 1001 al que pertenecen M2user1 y M2user2 como miembros secundarios.
  • M2extra Grupo con GID 1002 al que solo pertenece M2user1
  • M2user1 y M2user2 Son grupos privados creados por defecto para cada uno de los usuarios respectivos con GID 1003 y 1004.

4. Tabla resumen

Nombre de usuario M2user1
UID 1001
GID 1003
Grupo primario 1003 - M2user1
Grupos secundarios 1001 - M2shared
1002 - M2extra

Conclusiones

El comando id proporciona toda la información numérica y de control a nivel de núcleo que el sistema operativo utiliza para gestionar la seguridad y los permisos, más allá de la simple etiqueta de texto del nombre de usuario.

Los identificadores numéricos exactos UID y GID. Muestra el número de usuario uid=1001 y los números de grupo gid=1003, que son los valores reales que el kernel de Linux comprueba para autorizar o denegar el acceso a archivos y procesos.

La distribución entre grupos primarios y suplementarios. Detalla explícitamente cuál es el grupo principal y enumera todos los grupos secundarios a los que pertenece, incluyendo sus identificadores numéricos, enumerando los grupos asociados a la identidad consultada, cuyos GID pueden intervenir en las comprobaciones de acceso a recursos.

Fuente de información e identidad

  • id muestra los identificadores y grupos asociados al usuario consultado.
  • getent consulta las bases de los usuarios y grupos mediante NSS, que puede obtener la información de /etc/passwd y /etc/group, entre otras fuentes configuradas.

Experimento 2 - Grupo primario y grupos suplementarios

Hipótesis

Si se añade un usuario a un grupo adicional, ese grupo aparecerá entre sus grupos suplementarios.

Acción

1. Estado inicial

M2user2@ubuntu-lab:~$ id
uid=1002(M2user2) gid=1004(M2user2) groups=1004(M2user2),1001(M2shared)

2. Creación del grupo adicional

M2user2@ubuntu-lab:~$ exit
logout
ricardo@ubuntu-lab:~$ sudo groupadd M2extra2

3. Inclusión del usuario en el grupo adicional

ricardo@ubuntu-lab:~$ sudo usermod -aG M2extra2 M2user2

Resultado

ricardo@ubuntu-lab:~$ su - M2user2
M2user2@ubuntu-lab:~$ id
uid=1002(M2user2) gid=1004(M2user2) groups=1004(M2user2),1001(M2shared),1005(M2extra2)

Interpretación

El grupo principal: 1004(M2user2)

  • Grupo privado por defecto. Su GID primario.
  • Se crea automáticamente al dar de alta al usuario. Su función principal en el sistema es servir como propietario determinado para cualquier archivo o directorio nuevo que cree M2user2.

El grupo suplementario común: 1001(M2shared)

  • Grupo compartido al que pertenecen los usuarios del entorno de pruebas.
  • Canal de colaboración compartido. Permite que M2user2, junto con otros usuarios, comparta el acceso a archivos, carpetas o herramientas comunes organizados para ese grupo, sin necesidad de darles permisos globales a todo el sistema.

El grupo suplementario adicional: 1005(M2extra2)

  • Grupo añadido de forma dinámica y posterior mediante el comando usermod -aG
  • Demuestra la modificación en caliente de privilegios. Sirve para otorgar a M2user2 un rol, acceso o categoría extra que no tenía inicialmente.
  • Demuestra la hipótesis inicial. Al abrir una nueva sesión su - M2user2, el sistema lee la base de datos actualizada y carga este nuevo grupo dentro de sus credenciales activas

Experimento 3 - Identidad de un proceso

Hipótesis

Si se ejecuta un proceso con un usuario determinado, el proceso tendrá asociada la identidad de ese usuario

Preparación

  • Se emplea el proceso de control identity.py.
  • Se emplea la pseudoterminal pts/0 para ejecutar el proceso de control y la pseudoterminal pts/1 para inspeccionar el proceso.

Acción

1. Ejecución de identity.py desde pts/0 

M2user1@ubuntu-lab:~$ ./c1m2/identity.py
=== INFORMACIÓN DE CREDENCIALES DEL PROCESO ===
 PID (Process ID) : 2164
 UID (Real / Efectivo) : 1001 (M2user1) / [Efectivo: 1001]
 GID (Primario / Efect.) : 1003 (M2user1) / [Efectivo: 1003]
 Grupos Suplementarios : 1001 (M2shared), 1002 (M2extra), 1003 (M2user1)
================================================
El proceso se mantendrá en ejecución para inspección...
Pulsa Ctrl+C para finalizar.

2. Inspección del proceso identity.py desde pts/1 

ricardo@ubuntu-lab:~$ ps aux | grep identity.py
M2user1 2164 0.0 0.2 18116 10896 pts/0 S+ 19:24 0:00 python3 ./c1m2/identity.py
ricardo@ubuntu-lab:~$ cat /proc/2164/status | grep -E 'Uid|Gid|Groups'
Uid: 1001 1001 1001 1001
Gid: 1003 1003 1003 1003
Groups: 1001 1002 1003

Interpretación

Nexo de identidad: el UID numérico 1001

  • Evidencia en la cuenta (Estática). El archivo /etc/passwd vincula de forma unívoca el nombre de usuario M2user1 con el número 1001.
  • Evidencia en proceso (Dinámica). Al inspeccionar el proceso 2164 desde el sistema de archivos virtual del núcleo /proc/2164/status, se encuentra la línea: Uid: 1001 1001 1001 1001.
  • El núcleo asigna y verifica los permisos del proceso basándose estrictamente en el código numérico 1001, que coincide con el UID de la cuenta propietaria que muestra ps: M2user1

Nexo de pertenencia principal: el GID primario 1003

  • Evidencia en la cuenta (Estática). El registro de /etc/passwd para M2user1 fija su grupo principal con el identificador 1003 (M2user1).
  • Evidencia en el proceso (Dinámica). El archivo de estado del proceso expone: Gid: 1003 1003 1003 1003.
  • Cualquier recurso o archivo que cree el script identity.py heredará automáticamente el GID 1003 como grupo propietario, garantizando que opera bajo los parámetros nativos definidos en su cuenta.

Nexo de privilegios colectivos: los grupos suplementarios 1001 1002 1003

  • Evidencia en la cuenta (Estática). La combinación de /etc/passwd, grupo primario 1003, y /etc/group, pertenencia a M2shared (1001) y M2extra (1002), otorga al usuario un abanico de tres grupos.
  • Evidencia en el proceso (Dinámica). El núcleo refleja exactamente esta misma estructura de privilegios en el proceso activo: Groups: 1001 1002 1003.
  • Un proceso hereda íntegramente el contexto de seguridad de la sesión del usuario que lo invocó. El núcleo mapea los grupos de las bases de datos estáticas hacia los descriptores de acceso del proceso, permitiéndole interactuar con archivos compartidos de esos grupos M2shared y M2extra.

Conclusiones

  • La identidad y los grupos asociados al proceso pueden comprobarse mediante /proc/<PID>/status. Al iniciar una sesión, el sistema establece las credenciales del usuario; los procesos iniciados desde ella reciben normalmente esas credenciales a través de la herencia entre procesos. Los valores observados no son una lectura directa y continua de /etc/passwd y /etc/group.
  • La identidad de un proceso no es un nombre, sino una matriz de identificadores numéricos que provienen directamente de la cuenta de usuario.

Experimento 4 - Modificación de grupos mientras se ejecuta un proceso

Hipótesis

Si se modifica la pertenencia de un usuario a un grupo mientras existe un proceso suyo ya ejecutándose, el proceso no adopta automáticamente la nueva pertenencia.

Se produce una diferencia entre:

  • Identidad actual de la cuenta.
  • Credenciales/grupos del proceso ya existente.

Preparación

  • Se emplea el proceso de control identity.py
  • Se emplea la pseudoterminal pts/0 para ejecutar el proceso de control y las pseudoterminales pts/1 y pts/2 para las inspecciones que serán necesarias durante el experimento.

Acción

1. Ejecución del proceso identity.py desde pts/0 

M2user1@ubuntu-lab:~$ ./c1m2/identity.py
=== INFORMACIÓN DE CREDENCIALES DEL PROCESO ===
 PID (Process ID) : 6506
 UID (Real / Efectivo) : 1001 (M2user1) / [Efectivo: 1001]

ricardo@ubuntu-lab:~$ sudo usermod -aG M2extra2 M2user1
ricardo@ubuntu-lab:~$ su - M2user1
M2user1@ubuntu-lab:~$ groups
M2user1 M2shared M2extra M2extra2

 PID (Process ID) : 6571
 UID (Real / Efectivo) : 1001 (M2user1) / [Efectivo: 1001]
 GID (Primario / Efect.) : 1003 (M2user1) / [Efectivo: 1003]
 Grupos Suplementarios : 1001 (M2shared), 1002 (M2extra), 1003 (M2user1)
================================================

6. Ejecución del proceso identity.py desde pts/2 

M2user1@ubuntu-lab:~$ ./c1m2/identity.py
=== INFORMACIÓN DE CREDENCIALES DEL PROCESO ===
 PID (Process ID) : 6661
 UID (Real / Efectivo) : 1001 (M2user1) / [Efectivo: 1001]
 GID (Primario / Efect.) : 1003 (M2user1) / [Efectivo: 1003]
 Grupos Suplementarios : 1001 (M2shared), 1002 (M2extra), 1003 (M2user1), 1005 (M2extra2)
================================================
El proceso se mantendrá en ejecución para inspección...
Pulsa Ctrl+C para finalizar.

Interpretación

Verificación de la actualización a nivel de cuenta

Tras ejecutar la orden administrativa sudo usermod -aG M2extra2 M2user1 y abrir una nueva sesión con su - M2user1, el comando groups muestra de forma inmediata la inclusión en el nuevo grupo: M2user1 M2shared M2extra M2extra2

Los cambios en las bases de datos del sistema sí surten efecto de manera instantánea para las cuentas de usuario y sus futuras sesiones. Esto establece un contraste clave y directo con los procesos en ejecución, evidenciando que la cuenta y el proceso viven en planos de persistencia distintos.

Estado congelado del proceso antiguo PID 6506

A pesar de que en la cuenta de usuario ya se ejecutó usermod -aG M2extra2 M2user1 y una nueva sesión muestra el grupo nuevo, el comando cat /proc/6506/status | grep Groups devuelve: Groups: 1001 1002 1003
El volcado con ps confirma: SUPGRP: M2shared,M2extra,M2user1

El grupo M2extra2 brilla por su ausencia. Esto demuestra que los procesos heredan los grupos suplementarios de forma estática en el preciso instante en que son creados. Un cambio en las bases de datos del sistema /etc/group no afecta de forma retroactiva a los procesos que ya están corriendo.

Trampa del proceso intermedio PID 6571 y necesidad de nueva sesión

Antes de arrancar el PID 6571, la terminal /dev/pts/0 sigue siendo la misma donde se ejecuta el comando original, sin haber cerrado sesión su - M2user1.
Como resultado, el nuevo proceso 6571 se lanzó con los mismos grupos antiguos:
Grupos Suplementarios: 1001 (M2shared), 1002 (M2extra), 1003 (M2user1)

Demuestra un detalle sutil pero crítico: no basta con modificar el archivo en el sistema; la shell activa en esa ventana de terminal mantiene en su propia memoria los grupos que tenía cuando se autenticó por primera vez.
Para que la shell recoja los cambios de grupo es obligatorio abrir una nueva sesión.

Éxito del nuevo proceso PID 6661 con sesión actualizada

En la nueva terminal /dev/pts/2, tras iniciar una sesión limpia como M2user1, el script ejecutado como PID 6661 muestra por fin:
Grupos Suplementarios: 1001 (M2shared), 1002 (M2extra), 1003 (M2user1), 1005 (M2extra2)

Se valida por completo la hipótesis del laboratorio. Al iniciar una nueva sesión de usuario, el sistema lee las bases de datos actualizadas, y cualquier proceso hijo que nazca a partir de ese momento hereda el nuevo contexto de seguridad al completo, incorporando 1005 (M2extra2).

Conclusión
Las evidencias recabadas demuestran que no existe propagación retroactiva.

  • El proceso antiguo PID 6506 continúa ejecutándose con su matriz de grupos original Groups: 1001 1002 1003 a pesar de que la cuenta ya formaba parte de M2extra2.
  • Los permisos y credenciales de un proceso son una fotografía fija tomada exclusivamente en el momento exacto de su creación.
    Cualquier cambio administrativo posterior sobre la cuenta es invisible para los procesos vivos, requiriendo necesariamente el inicio de un nuevo proceso desde una sesión actualizada para que herede las nuevas credenciales.

Conclusiones generales

Linux mantiene la información de usuarios y grupos en sus bases de datos de identidad. Esta configuración establece el UID, el GID primario y la pertenencia a grupos suplementarios.
Herramientas como id y getent permiten consultar dicha información.

Cada proceso dispone de sus propias credenciales de usuario y grupo, que determinan su identidad y contribuyen a las decisiones de acceso a recursos.
Pueden inspeccionarse mediante /proc/<PID>/status.
Estas credenciales no se actualizan automáticamente cuando se modifica la pertenencia a grupos de la cuenta.

La sesión proporciona el contexto desde el que se inician los procesos.
Al crear un proceso, sus credenciales se establecen a partir de las del proceso que lo inicia, según las reglas de creación y configuración de credenciales de Linux. Por ello, una nueva sesión que incorpore los cambios de pertenencia a grupos puede iniciar procesos con credenciales actualizadas, mientras que los procesos existentes pueden conservar las anteriores.

Ante una incidencia de acceso, es necesario distinguir entre la configuración actual de la cuenta y las credenciales del proceso afectado.
Comparar ambas permite comprobar si el usuario pertenece al grupo requerido, si el proceso dispone de esa pertenencia y si es necesario iniciar una nueva sesión o volver a ejecutar la aplicación para que incorpore los cambios.

Resumen

El diagnóstico de incidencias de acceso en Linux exige relacionar la identidad configurada en la cuenta, las credenciales que conserva cada proceso y la sesión desde la que se inicia.
Comprobar estos tres niveles permite localizar discrepancias entre la configuración y el estado efectivo de ejecución, y determinar la acción correctiva adecuada.
