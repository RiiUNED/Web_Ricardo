Laboratorio M1T1 - Troubleshooting de un servicio Linux

SIGTERM, SIGKILL y reinicios con systemd

Investigación de un servicio Linux que no responde correctamente a una solicitud de parada y que se reinicia automáticamente después de una terminación forzada.

service-troubleshooting systemd journalctl linux-signals service-lifecycle

>_ Relevancia Operativa

Este laboratorio demuestra la capacidad práctica para investigar incidencias en servicios Linux mediante el análisis de su comportamiento, los registros de systemd y las señales utilizadas durante su ciclo de vida.

También demuestra la capacidad para identificar la causa de una terminación incorrecta, relacionar el comportamiento de un proceso con la configuración del servicio y verificar la corrección aplicada mediante herramientas como systemctl, journalctl y pgrep, incluyendo el análisis de políticas de reinicio como Restart=on-failure.

Contexto del incidente

  • Sistema: Ubuntu Server 24.04 LTS
  • Servicio: t1m01.service
  • Aplicación: proceso Python ejecutado como servicio mediante systemd

Durante las pruebas se observan dos comportamientos anómalos:

  • systemctl stop no consigue detener el servicio dentro del tiempo esperado.
  • La terminación forzada del proceso mediante kill -9 provoca que systemd inicie automáticamente una nueva instancia con un PID diferente.

Investigación y causa raíz

SIGTERM no provoca la terminación del proceso

1. Ejecución en pts/0

ricardo@ubuntu-lab:~/linux-lab/m01/t1m01$ sudo systemctl stop t1m01

2. Inspección de journalctl en pts/1 

Sep 28 14:08:09 ubuntu-lab systemd[1]: Stopping t1m01.service - Demonio de prueba para laboratorio t1m01...
Sep 28 14:08:09 ubuntu-lab python3[1597]: [14:08:09] [PID:1597] SEÑAL RECIBIDA (15). Ignorando petición de parada...
Sep 28 14:08:29 ubuntu-lab systemd[1]: t1m01.service: State 'stop-sigterm' timed out. Killing.
Sep 28 14:08:29 ubuntu-lab systemd[1]: t1m01.service: Main process exited, code=killed, status=9/KILL

3. Evidencias recabadas

  1. systemd inició la parada del servicio.
  2. El proceso recibió la señal 15 SIGTERM y ejecutó código de la aplicación en respuesta a ella.
  3. El proceso continuó ejecutándose después de recibir la señal.
  4. Transcurridos 20 segundos, systemd agotó el tiempo de espera de parada.
  5. systemd terminó entonces el proceso mediante SIGKILL.

4. Inspección del código de app.py

El programa tenía registrado un manejador para SIGTERM. 

# Capturar SIGTERM (15)
signal.signal(signal.SIGTERM, ignore_termination)

El manejador de la señal SIGTERM no termina el proceso. 

def ignore_termination(signum, frame):
 print(f"[{time.strftime('%H:%M:%S')}] [PID:{os.getpid()}] SEÑAL RECIBIDA ({signum}). 
 Ignorando petición de parada...")
Causa raíz. El manejador personalizado de SIGTERM procesaba la señal pero no iniciaba la terminación del proceso.

SIGKILL provoca el reinicio automático del servicio

1. Terminación directa del proceso y aparición de nueva instancia del proceso en pts/0 

ricardo@ubuntu-lab:~/linux-lab/m01/t1m01$ kill -9 1702
ricardo@ubuntu-lab:~/linux-lab/m01/t1m01$ pgrep -af app.py
1707 /usr/bin/python3 -u /home/ricardo/linux-lab/m01/t1m01/app.py

2. Inspección de journalctl desde pts/1 

Sep 28 14:43:29 ubuntu-lab systemd[1]: t1m01.service: Main process exited, code=killed, status=9/KILL
Sep 28 14:43:31 ubuntu-lab systemd[1]: t1m01.service: Scheduled restart job, restart counter is at 1.
Sep 28 14:43:31 ubuntu-lab systemd[1]: Started t1m01.service - Demonio de prueba para laboratorio t1m01.

3. Evidencias recabadas

  1. El proceso fue terminado mediante SIGKILL (kill -9).
  2. systemd registró la terminación como status=9/KILL.
  3. Dos segundos después, systemd programó un reinicio.
  4. Se inició una nueva instancia del servicio con un PID diferente.

4. Inspección de la configuración de la unidad

Durante la inspección se encuentra Restart=on-failure. Esta directiva establece que el servicio debe reiniciarse cuando el proceso termina en una condición considerada fallida.

Además, SIGKILL no puede ser capturada, bloqueada ni ignorada por el proceso. Por tanto, la aplicación no puede interceptar esta señal para ejecutar su propia lógica de cierre.

Causa raíz. La terminación del proceso mediante SIGKILL hizo que systemd registrara el servicio con resultado signal, y la directiva Restart=on-failure provocó automáticamente el arranque de una nueva instancia.

Correcciones aplicadas

Corrección incidencia: Parada mediante systemctl stop

Se modificó el manejador de señales de app.py para que SIGTERM provocara explícitamente la terminación del proceso: 

import signal
import sys

def graceful_shutdown(signum, frame):
 print(f"[{time.strftime('%H:%M:%S')}] [PID:{os.getpid()}] SEÑAL RECIBIDA ({signum}). 
 \nCierre ordenado.\nLiberando recursos...")
 sys.exit(0) #Salida limpia con código 0

# Capturar SIGTERM (15) y SIGINT (2)
signal.signal(signal.SIGTERM, graceful_shutdown)
signal.signal(signal.SIGINT, graceful_shutdown)

La llamada a sys.exit(0) termina el proceso Python con un estado de salida 0.

De esta forma, una solicitud normal de parada mediante systemctl stop deja de quedar bloqueada por un proceso que continúa ejecutándose después de recibir SIGTERM.

Corrección incidencia: Terminación mediante SIGKILL y reinicio automático

La causa del reinicio automático se encontraba en la política de reinicio configurada en la unidad:
Restart=on-failure

Para evitar que una terminación del proceso mediante SIGKILL provocara el arranque automático de una nueva instancia, se modificó la configuración del servicio para eliminar la política de reinicio automático:
[Service]
Restart=no

Verificaciones posteriores: Terminación mediante SIGKILL y reinicio automático
