Laboratorio M1T2 - Diagnóstico de procesos Linux

Investigación de procesos Linux que permanecen en estado zombie y fugas de descriptores de archivo mediante herramientas de diagnóstico del sistema.

process-diagnostics zombie-processes file-descriptors proc-filesystem strace

>_ Relevancia Operativa

Este laboratorio demuestra la capacidad práctica para investigar incidencias relacionadas con procesos Linux y consumo de recursos, partiendo del comportamiento observado y utilizando evidencias del sistema para determinar su causa.

Se aplican herramientas como ps, pstree, /proc, lsof y strace para identificar procesos zombie, analizar relaciones padre-hijo y detectar acumulación de descriptores de archivo. El diagnóstico se completa relacionando las evidencias obtenidas con el comportamiento del código y verificando posteriormente las correcciones aplicadas.

Contexto del incidente

  • Sistema: Ubuntu Server 24.04 LTS
  • Aplicaciones: scripts Atest.py y Btest.py
  • Área: procesos Linux y gestión de recursos

Durante las pruebas se observan dos comportamientos anómalos:

  • La ejecución de Atest.py genera procesos <defunct> que permanecen en la tabla de procesos.
  • La ejecución de Btest.py provoca una acumulación progresiva de descriptores de archivo abiertos.

Investigación y causa raíz

Acumulación de procesos <defunct>

1. Ejecución de Atest.py en pts/0

ricardo@ubuntu-lab:~/linux-lab/m01/t2m01$ ./Atest.py
[15:19:08] Proceso padre iniciado con PID: 1840

2. Inspección de la relación padre-hijo en pts/1

ricardo@ubuntu-lab:~$ pstree -p -N user
[4026531837]
bash(1040)
bash(1134)───python3(1840)───python3(1841)
ricardo@ubuntu-lab:~$ ps -o pid,ppid,stat,cmd -p 1840,1841
    PID    PPID STAT CMD
   1840    1134 S+   python3 ./Atest.py
   1841    1840 Z+   [python3] <defunct>
Observación. El proceso 1841 aparece en estado Z+ y tiene como proceso padre al proceso 1840, correspondiente a Atest.py. Esto confirma que el proceso <defunct> es un hijo del proceso principal.

3. Envío de SIGKILL desde pts/1

ricardo@ubuntu-lab:~$ kill -9 1841
ricardo@ubuntu-lab:~$ ps -o pid,ppid,stat,cmd -p 1840,1841
    PID    PPID STAT CMD
   1840    1134 S+   python3 ./Atest.py
   1841    1840 Z+   [python3] <defunct>

4. Evidencias recabadas

  1. El proceso 1840 crea un proceso hijo con PID 1841, como muestra la relación jerárquica obtenida mediante pstree.
  2. El proceso 1841 aparece con estado Z+ y marcado como <defunct>, indicando que ha finalizado su ejecución pero su entrada permanece registrada.
  3. El proceso 1841 tiene como PPID el PID 1840, confirmando que Atest.py es su proceso padre.
  4. El envío de SIGKILL mediante kill -9 al proceso 1841 no elimina su entrada: continúa apareciendo con estado Z+.
  5. El proceso padre 1840 permanece en estado S+ mientras su hijo 1841 permanece en estado <defunct>.

5. Inspección del código de Atest.py

# Proceso Hijo
print(f"[{time.strftime('%H:%M:%S')}] Proceso Hijo (PID:{os.getpid()}) ejecutando tarea rápida y finalizando...")
sys.exit(0)
# Proceso Padre
while True:
    time.sleep(5)
Causa raíz. Atest.py crea un proceso hijo que finaliza su ejecución, pero el proceso padre no recoge su estado de terminación mediante wait() o waitpid(). Como consecuencia, el hijo permanece como proceso zombie y, si el comportamiento se repite, pueden acumularse entradas <defunct> en la tabla de procesos.

6. Evidencias recabadas

  1. La traza de strace muestra sucesivas llamadas openat() sobre el mismo archivo test.txt, sin observarse llamadas close() que liberen los descriptores.
  2. La inspección de /proc/1711/fd muestra múltiples descriptores abiertos que apuntan simultáneamente a test.txt.
  3. La salida de lsof confirma que el proceso mantiene abiertos los descriptores 3 a 17 sobre test.txt.
  4. El proceso tiene establecido un límite blando de 1024 archivos abiertos, por lo que la retención continuada de descriptores puede provocar que el proceso alcance dicho límite.
  5. Las evidencias obtenidas confirman que los descriptores permanecen abiertos durante la ejecución del proceso, por lo que es necesario revisar el código de Btest.py para determinar qué operación provoca su apertura y por qué no son liberados.

7. Inspección del código de Btest.py

# Apertura de archivos
for i in range(15):
    f = open(open_file, "a")
    f.write(f"Registro de prueba {i}\n")
    open_files.append(f)
    time.sleep(5)
Causa raíz. Btest.py abre un nuevo descriptor de archivo en cada iteración y conserva el objeto de archivo en la lista open_files, pero no ejecuta close() sobre los archivos abiertos. Como consecuencia, los descriptores permanecen asociados al proceso y se acumulan mientras continúa la ejecución, pudiendo alcanzar el límite de archivos abiertos del proceso.

Correcciones aplicadas

Corrección incidencia: Acumulación de procesos <defunct>

Se modificó Atest.py para que el proceso padre recoja explícitamente el estado de terminación del proceso hijo mediante wait(): 

# Proceso Padre
pid, status = os.wait()

print(
    f"[{time.strftime('%H:%M:%S')}] "
    f"Proceso hijo {pid} finalizado con estado {status}"
)

while True:
    time.sleep(5)

La llamada a os.wait() bloquea al proceso padre hasta que uno de sus procesos hijos termina y, posteriormente, recoge su estado de terminación.

De esta forma, el proceso hijo no permanece como <defunct> y su entrada puede ser eliminada de la tabla de procesos.

Corrección incidencia: Acumulación de descriptores de archivo abiertos

Se modificó Btest.py para cerrar automáticamente el objeto archivo al finalizar cada operación de escritura mediante el gestor de contexto with: 

# Abrir el archivo y cerrar automáticamente el objeto archivo
try:
    for i in range(15):
        # Corrección en código Python
        with open(open_file, "a") as f:
            f.write("Registro con cierre automático de Descriptor\n")
        # El descriptor de archivo se cierra automáticamente al salir del bloque
        time.sleep(5)
except Exception as e:
    print(f"Error:{e}")

Al salir del bloque with, el objeto archivo se cierra automáticamente y el descriptor asociado se libera.

De esta forma, los descriptores utilizados en cada iteración no permanecen abiertos durante la ejecución del proceso y se evita su acumulación progresiva.
