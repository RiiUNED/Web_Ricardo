Laboratorio M1C1 - Señales

Investigación experimental del mecanismo de señales.

process-management linux-signals sigterm-vs-sigkill kernel-restrictions system-diagnostics

>_ Relevancia Operativa

Este laboratorio demuestra la capacidad práctica para identificar procesos en ejecución mediante herramientas como pstree, inspeccionar PIDs, intervenir sobre el flujo de ejecución mediante el comando kill y analizar las implicaciones del uso de SIGTERM, que permite al proceso gestionar una terminación ordenada, frente a la terminación forzada mediante SIGKILL.

También demuestra la capacidad de investigar un comportamiento inesperado y relacionarlo con las restricciones impuestas por el sistema operativo

Contexto y entorno

  • Sistema Operativo: Ubuntu Server 24.04 LTS
  • Virtualización: Oracle VM VirtualBox
  • Acceso: SSH (OpenSSH Server)
  • Máquina virtual: ubuntu-lab
  • Usuario: ricardo
  • Entorno de ejecución: Python 3.12.3

Objetivos

  • Analizar la comunicación entre el núcleo de Linux y los procesos mediante señales.
  • Investigar cómo las señales modifican el comportamiento por defecto de los procesos.
  • Estudiar cómo los procesos pueden tener distintos comportamientos ante una misma señal utilizando handlers.

Investigación

Modificación del comportamiento de procesos al recibir señales

  1. Ejecución de un proceso de control sin manejador para registrar el comportamiento por defecto.
  2. Intervención sobre el proceso mediante el envío de señales para observar la alteración del flujo.
  3. Implementación de un manejador de señales personalizado para evaluar la anulación de la acción por defecto.

Modificación del comportamiento de un proceso ante cualquier señal

Intento de interceptación y modificación de comportamiento sobre señales reservadas por el kernel.

Hipótesis

  • Caso Base: Proceso suspendido durante 2 minutos terminará de forma natural tras el tiempo especificado.
  • Intervención SIGTERM: Al recibir SIGTERM, el proceso sin manejador terminará de forma inmediata.
  • Manejador SIGTERM: El proceso con handler capturará la señal, imprimirá su identificador en la salida estándar y continuará en ejecución hasta completar su tiempo de suspensión.
  • Manejador SIGKILL / SIGSTOP: El proceso mantendrá el comportamiento por defecto del kernel, ignorando al manejador definido en el código.
  • Manejador SIGTERM y señal SIGKILL: Al estar el handler definido exclusivamente para SIGTERM, la recepción de SIGKILL no ejecutará el handler; el proceso mantendrá el comportamiento predeterminado asociado a SIGKILL, su terminación inmediata.

Procesos utilizados

Proceso sin manejador de señales testNoH.py

#!/usr/bin/env python3
import sys, time
print("Ejecución de test")
if len(sys.argv) > 1:
    time.sleep(int(sys.argv[1]))
print("Fin de la ejecución de test")

El proceso imprime un mensaje de inicio, suspende su ejecución durante los segundos indicados por argumento y finalmente imprime el mensaje de cierre.

Proceso con manejador de señales testH.py

#!/usr/bin/env python3
import sys, time, signal

def handler(signum, frame):
    print(signum)

signal.signal(signal.SIGTERM, handler)
print("Ejecución de test")
if len(sys.argv) > 1:
    time.sleep(int(sys.argv[1]))
print("Fin de la ejecución de test")

Proceso análogo al anterior que intercepta la señal SIGTERM mediante la función handler(), imprimiendo el identificador numérico de la señal sin finalizar el proceso.

Manejador SIGTERM: El proceso con handler capturará la señal, imprimirá su identificador en la salida estándar y continuará en ejecución hasta completar su tiempo de suspensión.

    • ricardo@ubuntu-lab:~$ ./linux-lab/l01.1/testNoH.py 180

  • Con manejador: Captura de la señal e impresión de su código numérico 15, manteniendo la ejecución hasta completar el temporizador. 
    • ricardo@ubuntu-lab:~$ ./linux-lab/l01.1/testH.py 180
Ejecución de test
15
Fin de la ejecución de test

Interpretación

Cuando el proceso recibe la señal, se ejecuta el handler: 

signal.signal(signal.SIGTERM, handler)

El manejador de señales imprime el código numérico de la señal recibida: 

def handler(signum, frame):
    print(signum)

En la salida estándar que recibe información del proceso, se imprime el código de la señal, pero el proceso no termina al recibir la señal, termina de forma natural cuando han pasado los 3 minutos que se le pidió que estuviera dormido. 

ricardo@ubuntu-lab:~$ ./linux-lab/l01.1/testH.py 180
Ejecución de test
15
Fin de la ejecución de test

Conclusión

Se cumple la hipótesis de partida
El proceso con handler capturará la señal, imprimirá su identificador en la salida estándar y continuará en ejecución hasta completar su tiempo de suspensión.

Experimento 2 - SIGKILL

Hipótesis

Manejador SIGKILL / SIGSTOP: El proceso mantendrá el comportamiento por defecto del kernel, ignorando al manejador definido en el código.

Preparación

Modificación del archivo de script para registrar la señal reservada SIGKILL. 

ricardo@ubuntu-lab:~$ cat linux-lab/l01.1/testH.py
#!/usr/bin/env python3
import sys, time, signal

def handler(signum, frame):
    print(signum)

signal.signal(signal.SIGKILL, handler)
print("Ejecución de test")
if len(sys.argv) > 1:
    time.sleep(int(sys.argv[1]))
print("Fin de la ejecución de test")

Intervención y resultado

El intérprete de Python impide la ejecución del proceso al detectar un error al registrar el manejador. 

ricardo@ubuntu-lab:~$ ./linux-lab/l01.1/testH.py 180
Traceback (most recent call last):
  File "/home/ricardo/./linux-lab/l01.1/testH.py", line 8, in <module>
    signal.signal(signal.SIGKILL, handler)
  File "/usr/lib/python3.12/signal.py", line 58, in signal
    handler = _signal.signal(_enum_to_int(signalnum), _enum_to_int(handler))
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
OSError: [Errno 22] Invalid argument

Investigación

Al ejecutar el script, el módulo signal de Python solicita al sistema operativo que establezca un manejador para la señal indicada. Para ello, la implementación de Python utiliza la interfaz de señales proporcionada por la biblioteca C/POSIX, que finalmente interactúa con el kernel de Linux mediante la interfaz de llamadas al sistema correspondiente.

  1. La implementación de Python solicita establecer un manejador para SIGKILL (señal 9).
  2. El kernel de Linux valida la solicitud. SIGKILL es una señal especial cuyo comportamiento no puede ser modificado por un proceso: no puede ser capturada, bloqueada ni ignorada. Por ello, la solicitud de establecer un manejador para SIGKILL es rechazada y la operación falla con el error EINVAL (Invalid argument).
  3. La implementación de Python detecta el fallo de la operación del sistema y lo traduce a una excepción OSError. Por eso, el programa muestra: 
    OSError: [Errno 22] Invalid argument

El valor 22 corresponde a EINVAL, que indica que uno de los argumentos proporcionados a la operación no es válido para esa operación.

Conclusión

La hipótesis no puede verificarse en los términos planteados
El proceso no llega a ejecutarse porque el intento de registrar un handler para SIGKILL es rechazado. El resultado confirma que SIGKILL no puede ser capturada mediante un manejador de señales.

Experimento 3 - Envío de SIGKILL a un proceso con handler SIGTERM

Hipótesis

Manejador SIGTERM y señal SIGKILL: Al estar el handler definido exclusivamente para SIGTERM, la recepción de SIGKILL no ejecutará el handler; el proceso mantendrá el comportamiento predeterminado asociado a SIGKILL, su terminación inmediata.

  • pts/0: Inspección de PID y emisión de señales.

signal.signal(signal.SIGTERM, handler)

Conclusiones generales

En este laboratorio se investigó la relación entre procesos y señales y cómo los manejadores de señales pueden modificar el comportamiento de los procesos al recibir algunas señales.

También se investigó qué ocurre cuando se intenta modificar el comportamiento de los procesos con manejadores de señales con señales que no pueden ser capturadas ni ignoradas.

Se crearon procesos con manejadores de señales y se analizó su comportamiento al recibir distintas señales, incluyendo el intento de registrar un manejador para SIGKILL.

Se observó cómo los procesos pueden modificar su comportamiento cuando tienen manejadores de señales y cómo algunas señales, SIGKILL en este laboratorio, no pueden ser capturadas ni ignoradas.

Resumen:

  • Las señales son el mecanismo estándar de notificación asíncrona entre el kernel y los procesos en sistemas UNIX/Linux.
  • Un proceso puede interceptar señales estándar (como SIGTERM) mediante manejadores para asegurar cierres limpios o redefinir su respuesta.
  • Las señales SIGKILL y SIGSTOP están protegidas a nivel del sistema operativo para permitir a los administradores de sistemas y al propio kernel detener procesos desbocados de forma determinista.
